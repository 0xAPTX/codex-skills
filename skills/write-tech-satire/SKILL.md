# 科技讽刺寓言

把真实矛盾写成一个能独立成立的小故事：人物认真、语言平静、细节具体，让人物越努力解决眼前问题，越暴露规则与利益之间的荒诞。笑点来自行为的逻辑，不靠作者站出来宣布谁愚蠢。

## 找到故事的受力点

先判断谁控制入口、谁付钱、谁劳动、谁承担风险，以及他们各自声称在追求什么。从一个最有力的矛盾入手，不必把所有问题写进一段。

可选机制，按题材取用，不逐项套模板：

- **付费不等于被接纳**：角色供奉服务，又自费伪装成有资格使用服务的人。
- **适应规则变成自我改造**：为了让电脑像美国用户，给电脑编的人生比本人履历还完整。
- **幸存被当成保证**：把过去没出事当作未来安全的证明，甚至写成指南出售。
- **流程只约束服从者**：攻击者绕过审批，整改却给内部员工再加一道审批。
- **成本与价值错配**：不愿为基础维护付费，却肯为事故评估和漂亮报告花钱。
- **救火成功抹去救火价值**：人把问题解决了，组织据此证明不再需要这个人。

寓言可以用农场、神庙、村庄、木匠，也可以直接写公司和程序员。保持一个主要隐喻，别把每个技术名词都强行映射成动物或宗教用品。不要把“火鸡”当成固定角色。

## 写法

- 开头尽快交代人物的愿望和一个具体矛盾，少讲背景大道理。
- 用两三件有递进关系的事推动故事。每次应对在角色自身的利益或信念里说得通，合起来却越来越荒唐。
- 放入少量只属于这个题材的细节，例如托管 Mac mini、浏览器指纹、工单、发布窗口、免费门锁。细节应参与因果，别堆术语。
- 人物说正经话，作者少用愤怒形容词。需要时借用“用户体验”“知识沉淀”“流程闭环”等话术，让行为自行拆穿它。
- 结尾用一个动作、一句通知、一项指标或一句平静回复，回扣前面的道具和规则。最后一句出来就收笔，不再解释寓意。
- 可以温和、辛辣或黑色幽默，按用户要求调整。锋芒主要指向权力、利益与制度的矛盾，不把受限制者的国籍或身份本身写成笑点。

默认直接交付正文。单篇通常约 200–450 个汉字，够用就停；用户只要一句梗就压缩，要求长篇再展开。用户泛问“还有别的吗”时，可给 2–3 篇不同切口；同一机制换主语不算新角度。不必固定加标题、分析或创作说明。

## 涉及近期事件

用户提到“最近”“这次漏洞”或具体新闻时，先核实事件；技术事实优先查官方公告、项目维护者和原始披露。只提取故事需要的少量事实，不写成新闻综述。

- 保留事实边界：某些配置受影响不等于全网都能被接管，发现漏洞不等于已经攻破所有网站。
- 新闻背景与虚构情节分开。必要时在正文前用一句话说明经核实的背景并附来源，交代后文为借题发挥；引用不插进笑点里。
- 虚构人物的台词与行为不要冒充真实机构的原话或真实事故。不要把旧范例中的日期、编号和技术细节当作新热点事实复用。
- 用户提供完整素材且只要求改写时，可依素材创作；发现关键事实疑点则核实或改成明确的假设情境。无法核实时不编造新闻。

## 交付前修剪

检查角色行为是否有动机、升级是否有因果、结尾是否回扣。删掉重复铺垫和“这说明了”“真正的问题是”等寓意解说。

避免只复述“PHP 是世界上最好的语言”等熟梗；避免每篇都以封号、裁员、收费或 token 计数收尾。若换成任何公司或技术都成立，补回本题特有的矛盾与细节。

用户要求沿用本次对话语感，或需要校准成稿质量时，阅读 [references/examples.md](references/examples.md)。学它的因果与节奏，另写新情节，不机械复制标志性句子。
